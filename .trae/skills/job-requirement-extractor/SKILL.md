# 岗位硬性要求提取器

读取 BOSS直聘搜索结果 Markdown 文件（由 `boss_search.py` 生成的 `*.md` 文件），解析每个职位的详情区块，从职位描述中提取**硬性要求**（学历、经验、专业、技能、证书、行业背景、优先条件等），**在每个职位详情的 `> [!info]` callout 之后新增一个 `> [!check] 硬性要求` callout 模块**，就地写回源文件。

## 适用文件结构

输入文件必须符合 BOSS直聘搜索结果的标准结构：

```
---
frontmatter（含 tags, title, query, city, source, count, createTime, status）
---

# BOSS直聘搜索 - {公司名}

> **关键词**: ... | **城市**: ... | **数量**: ... | **时间**: ...

## 职位列表

| # | 职位 | 薪资 | 公司 | 地区 | 经验 | 学历 | 职位描述 | securityId |
|---|------|------|------|------|------|------|------|------|
| 1 | ... | ... | ... | ... | ... | ... | ... | ... |

## 职位详情

### 1. {职位名}

> [!info] 职位详情
> **公司**: ...
>
> **职位描述**:
>
> - {职责/要求内容}

### 2. {职位名}
...
```

## 硬性要求维度

从每个职位的职位描述中提取以下维度的硬性要求：

| 维度 | 说明 | 示例 |
|------|------|------|
| 学历 | 最低学历要求 | 本科及以上、大专、学历不限 |
| 专业 | 相关专业要求 | 电子、自动化等相关专业 |
| 经验 | 工作经验年限及领域 | 3-5年小家电行业硬件开发经验 |
| 行业 | 行业背景要求 | 有母婴用品厂家工作经验 |
| 技能 | 必备技能/工具 | 精通数模电路设计，熟练使用 AD/Cadence |
| 证书 | 资质证书要求 | 持有叉车证者优先 |
| 优先 | 加分/优先条件 | 有 BLDC 驱动设计经验者优先 |
| 其他 | 其他硬性条件 | 能适应倒班、无经验勿扰 |

**数据来源优先级**：
1. 职位详情中的「任职要求」「任职资格」「技能要求」「能力要求」等明确区块
2. 职位列表表格中的「经验」「学历」列（作为补充和交叉验证）
3. 职位描述正文中隐含的硬性条件（如「无经验勿扰」「能适应倒班」）

## 输出格式

在每个职位的 `> [!info] 职位详情` callout 结束后、下一个 `###` 标题之前，插入一个 `> [!check] 硬性要求` callout：

```markdown
### 1. 项目经理

> [!info] 职位详情
> **公司**: 布童科技 · 电子商务 · 500-999人 · B轮
>
> **职位描述**:
>
> - 职责描述：...（原有内容保持不变）

> [!check] 硬性要求
> - **学历**：本科及以上
> - **经验**：3~5年以上母婴用品厂家或电商平台母婴板块工作经验
> - **行业**：母婴用品厂家或电商平台母婴板块
> - **技能**：熟悉产品开发流程与技术工艺，有一定供应商资源
> - **优先**：有孩子王、可优比、贝恩施、Babycare 等母婴类企业从业背景者优先

### 2. Android
...
```

**格式规范**：
- callout 类型固定为 `[!check]`，标题固定为 `硬性要求`
- 每条要求用 `> - **{维度}**：{内容}` 格式
- 仅列出该职位明确提及的维度，无提及的维度不列出
- 若职位描述极其简略（如仅有职责无要求），从表格列补充学历和经验，并标注「（来自表格）」
- 若完全无法提取任何硬性要求，写入 `> - 暂无明确硬性要求`

## 属性标记规则

为避免对同一文件重复提取，本 skill 会在文件 frontmatter 中写入属性 `requirements_generated`。

- **属性名**：`requirements_generated`
- **属性值**：
  - 成功生成硬性要求模块时：写入当前时间戳，如 `2026-07-28 15:30:12`
  - 确认无职位详情时：写入 `无`
- **为空判定**：属性不存在、值为空字符串、值为 `null`、值为 `~` 均视为空，可以提取
- **非空判定**：属性已设置且值为非空字符串（包括 `无` 和时间戳），则跳过该文件
- **重新生成**：用户要求重新提取时，手动清空该属性即可让文件重新进入提取流程

## 工作流程

### Step 1: 确认输入文件

询问用户提供 BOSS直聘搜索结果 Markdown 文件路径（如 `d:\obsidian\demo\05_long_project\BOSS直聘\布童科技_宁波.md`）。

也支持用户提供目录路径，此时使用 `Glob` 扫描该目录下的 `*.md` 文件（排除 `待办/`、`笔记/` 子目录），逐个处理。

### Step 2: 读取文件并检查 `requirements_generated` 属性

使用 `Read` 工具读取目标文件的完整内容。

**属性检查**：读取后立即检查文件 frontmatter 中的 `requirements_generated` 属性：

- 若文件以 `---` 开头，解析首个 `---` 结束前的 YAML frontmatter
- 若 `requirements_generated` 存在且值为非空字符串（包括时间戳或 `无`），则**跳过该文件**，不执行提取
- 若属性为空、不存在、值为 `null` 或 `~`，则继续后续流程

### Step 3: 解析文件结构

从文件内容中解析出以下结构信息：

1. **职位列表表格**（`## 职位列表`）：
   - 提取表格的每一行，记录每个职位的序号、职位名、经验、学历
   - 构建 `table_info = {序号: {职位名, 经验, 学历}}` 映射
2. **职位详情区块**（`## 职位详情`）：
   - 按 `### {序号}. {职位名}` 分割出每个职位的详情区块
   - 记录每个区块的起止行号（用于后续插入定位）
   - 提取每个区块内的 `> [!info] 职位详情` callout 内容
3. **排序异常处理**：
   - 职位详情区块的顺序可能与表格序号不一致（如位置 7 排在位置 15 之后）
   - 以 `### {序号}.` 中的序号为唯一标识，不依赖出现顺序

**结构校验**：
- 确认文件包含 `## 职位列表` 和 `## 职位详情` 两个二级标题
- 确认至少有 1 个职位详情区块
- 若文件结构不符合预期，报告错误并终止

### Step 4: 逐职位提取硬性要求

**按职位逐个处理**：为每个职位独立提取硬性要求，不跨职位合并。

对每个职位，从以下来源提取硬性要求：

**来源 A — 职位描述中的明确要求区块**：

识别职位描述中以下关键词引导的区块，从中提取硬性要求：
- `任职要求`、`任职资格`、`岗位要求`、`任职条件`
- `技能要求`、`能力要求`、`岗位条件`
- `加分项`、`优先条件`、`优先考虑`

提取规则：
- 逐条阅读每个编号项（`1.`、`2.`、`3.`）或列表项（`-`）
- 判断每条内容属于哪个维度（学历/经验/专业/行业/技能/证书/优先/其他）
- **学历判定**：包含「本科」「大专」「硕士」「博士」「学历」「学历不限」等关键词
- **经验判定**：包含「年」「经验」「工作经验」「从业」等关键词，或年限数字
- **专业判定**：包含「专业」「相关」「学科」等关键词
- **行业判定**：包含「行业」「领域」「板块」「从业背景」等关键词
- **技能判定**：包含「精通」「熟练」「熟悉」「掌握」「使用」「操作」等技能动词
- **证书判定**：包含「证书」「资格证」「持证」「执业」等关键词
- **优先判定**：包含「优先」「加分」「者优先」「prefer」等关键词
- **其他**：不属于以上维度但属于硬性条件（如「能适应倒班」「无经验勿扰」「抗压强」）

**来源 B — 表格列补充**：

从 `## 职位列表` 表格中提取该职位的「经验」和「学历」列：
- 若职位描述中未明确提及学历/经验，使用表格列的值补充
- 补充的值标注 `（来自表格）`，如 `> - **学历**：本科（来自表格）`
- 若表格列值为「学历不限」「经验不限」，仍需列出（表明无硬性学历/经验门槛）

**来源 C — 正文中隐含的硬性条件**：

扫描职位描述全文，识别以下隐含硬性条件：
- `无经验勿扰` → **其他**：无经验勿扰
- `能适应倒班` / `能适应长时间站立` → **其他**：能适应倒班/长时间站立
- `抗压强` / `能承受工作压力` → **其他**：抗压能力强
- `早九晚六 周末双休` → 不属于硬性要求，跳过（这是福利信息）
- `上市公司` / `领导好` → 不属于硬性要求，跳过（这是公司介绍）

**🔴 最高原则：忠于原文，不臆造要求**

- 硬性要求必须**直接来源于职位描述或表格**，不得凭经验补全
- 若职位描述极其简略（如仅有职责列表无要求），仅从表格补充学历和经验
- 每条要求必须能在原文中找到明确出处
- **宁缺毋滥**：不确定是否为硬性要求时，不提取

### Step 4.5: 提取完整性二次校验（🔴 必执行，不可跳过）

**目的**：防止硬性要求提取不完整，遗漏关键条件。这是最常见的质量问题。

**位置**：Step 4 之后、Step 5 之前。

**核心机制**：对每个职位执行 5 项自检清单，逐项确认提取完整性。

**执行流程**：

1. **逐职位回读校验**：

   对每个职位，重新审视其职位描述全文，执行以下检查：
   - 重新阅读所有「任职要求」「任职资格」等区块中的**每一条**
   - 检查是否有条件被错误合并（如将「本科及以上」和「3-5年经验」合并为一条）
   - 检查是否有条件被遗漏（如「能适应倒班」「无经验勿扰」等隐含条件）
   - 检查表格中的学历/经验是否已被纳入（除非职位描述中已明确提及）

2. **完整性自检清单**（对每个职位逐项确认）：

   - [ ] 「任职要求/任职资格」区块中的每一条编号项是否都已提取？
   - [ ] 表格中的「学历」和「经验」列是否已纳入（或已在描述中找到对应）？
   - [ ] 职位描述中的隐含硬性条件（倒班、无经验勿扰等）是否已提取？
   - [ ] 「优先/加分项」是否已单独归入「优先」维度？
   - [ ] 是否存在将多个条件错误压缩为一条的情况？

3. **补漏机制**：

   - 若二次校验发现遗漏条件，立即补充到该职位的候选要求列表中
   - 若二次校验发现某条要求是多个条件的错误压缩，拆分为多条独立要求
   - 记录校验结果：`职位{序号}：初次提取{N}条，二次校验补充{M}条，最终{N+M}条`

4. **严禁的错误模式**（基于历史问题总结）：

   - ❌ 任职要求有 6 条，只提取了 3 条 → 必须全部提取
   - ❌ 表格标注「本科」但职位描述未提及学历，未补充表格信息 → 必须补充
   - ❌ 「无经验勿扰」这种硬性门槛被遗漏 → 必须提取到「其他」维度
   - ❌ 将「本科及以上，3-5年经验」合并为一条 → 必须拆分为学历+经验两条

### Step 5: 为每个职位组织硬性要求模块

为每个职位规划 `> [!check] 硬性要求` callout 的内容。

**模块模板**：

```markdown
> [!check] 硬性要求
> - **学历**：{学历要求}
> - **经验**：{经验要求}
> - **专业**：{专业要求}
> - **行业**：{行业要求}
> - **技能**：{技能要求}
> - **证书**：{证书要求}
> - **优先**：{优先条件}
> - **其他**：{其他硬性条件}
```

**组织规则**：
- 仅列出该职位明确提及的维度，无提及的维度不列出
- 维度顺序固定：学历 → 专业 → 经验 → 行业 → 技能 → 证书 → 优先 → 其他
- 每条要求简洁明确，保留原文中的关键信息（年限、工具名、行业名等）
- 从表格补充的信息标注 `（来自表格）`
- 若某维度有多条要求，合并为一条用分号分隔
- 若完全无法提取任何硬性要求：`> - 暂无明确硬性要求`

**示例 — 职位 9（电子工程师）**：

```markdown
> [!check] 硬性要求
> - **学历**：本科及以上
> - **专业**：电子、自动化等相关专业
> - **经验**：3-5年以上小家电、智能穿戴或消费电子（3C）行业硬件开发经验
> - **技能**：精通数模电路设计；熟练使用 AD/Cadence/PADS 等设计软件；熟悉 MCU（STM32/ESP32等）外围电路设计
> - **优先**：有无刷电机（BLDC）驱动设计经验，或非接触式传感器（如雷达、压电薄膜）开发经验者优先
```

**示例 — 职位 5（注塑工）**：

```markdown
> [!check] 硬性要求
> - **学历**：学历不限（来自表格）
> - **经验**：经验不限（来自表格）；有制造业相关工作经验者优先
> - **其他**：身体健康，能适应倒班或长时间站立工作
> - **优先**：有制造业相关工作经验者优先考虑
```

**示例 — 职位 2（Android，描述极简）**：

```markdown
> [!check] 硬性要求
> - **学历**：本科（来自表格）
> - **经验**：1-3年（来自表格）
> - 暂无更多明确硬性要求
```

### Step 6: 获取时间戳

使用 `RunCommand` 获取当前时间戳：

```powershell
Get-Date -Format "yyyy-MM-dd HH:mm:ss"
```

### Step 7: 写入源文件（🔴 原子写入）

**核心原则**：必须使用 `Read` → 内存中合并所有修改 → 单次 `Write` 的原子写入模式，禁止多次 `Edit`。

#### 7.1 构建完整文件内容

1. **已在 Step 2 读取了文件完整内容**，将其保留在内存中
2. **定位插入点**：对每个职位详情区块，找到其 `> [!info] 职位详情` callout 的结束位置
   - callout 结束标志：下一行不以 `>` 开头，或遇到下一个 `###` 标题，或遇到空行后非 `>` 行
3. **插入硬性要求模块**：在 callout 结束后、下一个 `###` 标题之前，插入一个空行 + `> [!check] 硬性要求` callout + 空行
4. **处理已存在模块**：
   - 若该职位下已存在 `> [!check] 硬性要求` callout（重新生成场景）：替换旧模块内容
   - 若不存在：在 `> [!info]` callout 后插入新模块
5. **在内存中完成所有职位的插入/替换操作**

#### 7.1.5 源文件写入后回读校验（🔴 必执行，不可跳过）

**目的**：确保写入后的文件中，每个职位下确实包含硬性要求模块，且模块内容完整。

**位置**：Step 7.1 构建内容之后、Step 7.2 实际写入之前——此处先对内存中的构建结果进行预校验；写入后再对实际文件进行回读校验。

**执行流程**：

1. **预校验（写入前）**：
   - 在内存中构建的完整文件内容中，搜索所有 `> [!check] 硬性要求` callout
   - 统计实际模块数量：`actual_module_count`
   - 与 Step 3 解析出的职位数量对比
   - 若不一致：检查是否有职位的插入点定位错误，修正后重新校验

2. **回读校验（写入后）**：
   - 使用 `Read` 工具重新读取写入后的文件
   - 提取所有 `> [!check] 硬性要求` callout 的实际内容
   - 对每个模块，统计其包含的 `> - **` 行数（即维度条目数）
   - 与 Step 5 计划的维度条目数对比
   - **禁止使用计划阶段记忆的条目数**，必须以回读结果为准

3. **输出校验结果**：

   对每个职位输出：
   ```
   职位{序号} {职位名} 回读校验：
     实际维度条目：{N} 条
     与计划一致性：一致 / 不一致（已修正）
   ```

#### 7.2 原子写入规则（🔴 必须遵守）

**问题解决**：多次 `Edit` 操作同一文件会导致内容错位、重复或丢失（历史教训）。

**核心机制**：

- **禁止对源文件执行多次 `Edit` 操作**：每个职位的模块插入不得使用单独的 `Edit` 调用
- **必须使用 `Write` 工具一次性写入完整文件内容**：
  1. 在 Step 2 已读取文件完整内容
  2. 在内存中对每个职位区块执行插入/替换操作（Step 7.1）
  3. 执行预校验（Step 7.1.5）
  4. 用一次 `Write` 调用写入合并后的完整文件内容
- **批量处理约束**：当文件包含多个职位时，所有职位的模块插入必须在同一次 `Write` 中完成
- **禁止的模式**：
  - ❌ 对文件执行 15 次 `Edit`（每个职位一次）→ 任何一步失败都会导致文件状态不一致
  - ❌ 先插入职位 1 的模块并写入，再插入职位 2 的模块并再次写入 → 第二次写入可能覆盖第一次的部分修改
- **正确的模式**：
  - ✅ 读取文件 → 在内存中为所有职位插入模块 → 一次 `Write` 写入完整内容

#### 7.3 更新 frontmatter 属性

在写入文件时，同步更新 frontmatter 中的 `requirements_generated` 属性：

- **若本次成功生成了硬性要求模块**：属性值设为当前时间戳
- **若本次确认无职位详情**：属性值设为 `无`
- 写入方式：
  - 如果文件已有 frontmatter（以 `---` 开头）：
    - 若其中已存在 `requirements_generated:` 行，更新其值
    - 若不存在，在 frontmatter 结束行 `---` 之前插入一行 `requirements_generated: <值>`
  - 如果文件没有 frontmatter：在文件最开头插入 frontmatter 块

### Step 8: 三重验证（🔴 必执行）

**验证 1 — 职位模块完整性**：
- 回读写入后的文件
- 统计 `> [!check] 硬性要求` callout 的数量
- 与 Step 3 解析出的职位详情数量对比
- 若不一致：检查是否有职位的模块遗漏，必要时重新写入

**验证 2 — 模块内容一致性**：
- 回读每个 `> [!check] 硬性要求` callout 的实际内容
- 提取每个模块中的维度条目（`> - **{维度}**`）
- 与 Step 5 计划的维度列表逐职位对比
- 若不一致：以回读实际内容为准，报告差异

**验证 3 — 原有内容未被破坏**：
- 回读文件，确认以下内容完整无损：
  - frontmatter 完整（原有属性 + 新增 `requirements_generated`）
  - `## 职位列表` 表格完整
  - 每个 `### {序号}. {职位名}` 标题完整
  - 每个 `> [!info] 职位详情` callout 内容完整
  - `securityId` 注释完整
- 若发现原有内容被破坏：从 Step 2 读取的原始内容恢复，重新执行 Step 7

### Step 9: 报告结果

向用户报告处理情况：

- 文件路径
- 职位总数
- 成功提取硬性要求的职位数
- 每个职位的维度条目数概览
- 因 `requirements_generated` 非空而跳过的文件
- 可点击的文件链接（使用 `computer://` 协议）

## 补充模式工作流（重新提取已有硬性要求的文件）

**触发场景**：用户要求「重新提取」或「补充」已有硬性要求的文件（`requirements_generated` 非空），通常是因为新增了职位或原提取不完整。

**与正常流程的区别**：不重新生成所有模块，而是保留已有模块中对的职位，仅对新增职位或内容有变的职位更新。

### S1: 读取源文件并解析已有模块

1. 使用 `Read` 读取源文件完整内容
2. 扫描所有 `> [!check] 硬性要求` callout，记录已有模块的职位序号和内容
3. 扫描所有 `### {序号}.` 标题，记录当前文件中的全部职位序号

### S2: 识别需要处理的职位

对比已有模块的职位序号与当前全部职位序号：
- **新增职位**（有 `###` 标题但无硬性要求模块）：需要提取
- **已有模块的职位**：默认跳过，除非用户明确要求重新提取

### S3: 对新增职位执行 Step 4-5

对每个新增职位，执行正常的硬性要求提取流程（Step 4 + Step 4.5 + Step 5）。

### S4: 原子更新源文件

1. 在内存中为新增职位插入硬性要求模块
2. 更新 `requirements_generated` 属性为当前时间戳
3. 一次 `Write` 写入完整文件内容

### S5: 回读校验（执行 Step 7.1.5）

回读源文件，确认新增职位的模块已正确插入，已有模块未被破坏。

### S6: 三重验证（执行 Step 8）

执行完整的三重验证流程。

### S7: 报告结果

报告新增处理的职位数量和跳过的职位数量。

## 注意事项

- **就地写入原则**：硬性要求模块直接写入源文件中对应职位下，不创建新文件，不创建汇总文件。
- **原文保护**：写入操作不得修改或删除源文件的任何原有内容（frontmatter 属性更新除外），仅在 `> [!info]` callout 后新增 `> [!check]` callout。
- **不臆造要求**：所有硬性要求必须基于职位描述或表格内容，不要凭空生成原文未提及的条件。
- **保留原文语义**：要求表述应忠实于原文意图，不要过度改写导致语义偏移。保留原文中的年限、工具名、行业名等具体信息。
- **表格补充标注**：从表格列补充的学历/经验信息必须标注 `（来自表格）`，与职位描述中明确提及的要求区分。
- **简略描述处理**：若职位描述极简（如仅有职责无要求），仅从表格补充学历和经验，并注明「暂无更多明确硬性要求」。
- **callout 格式**：硬性要求模块使用 `> [!check]` 类型 callout，与职位详情的 `> [!info]` 类型区分，视觉上便于识别。
- **大文件处理**：若单个文件超过 2000 行，分段读取并合并处理结果。
- **`requirements_generated` 属性**：
  - 该属性是控制重复提取的唯一依据，手动清空该属性可让文件重新进入提取流程
  - 成功生成硬性要求后写入时间戳，确认无职位详情后写入 `无`，两种值都会使下次扫描跳过该文件
- **与 todo-generator / note-generator 并存**：同一源文件可同时拥有 `## 待办`、`## 笔记` 和 `> [!check] 硬性要求` 模块，三个 skill 互不干扰，各自管理各自的属性。
- **职位排序异常**：BOSS直聘文件中职位详情区块的顺序可能与表格序号不一致，以 `### {序号}.` 中的序号为唯一标识，不依赖出现顺序。
